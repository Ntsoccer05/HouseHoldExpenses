# DB性能問題の見つけ方・直し方（初心者向け）

このドキュメントは、`/api/monthly-transactions-bulk` と `/api/getTransactions` が遅かった実際の調査・修正を題材に、「なぜ遅くなるのか」「どうやって原因を見つけたのか」「なぜその直し方で速くなるのか」を、DB設計初心者向けに解説するものです。

調査の具体的な手順（コマンド例など）は [`performance-investigation`スキル](../.claude/skills/performance-investigation/SKILL.md) にまとめてあります。このドキュメントは**手順**より**なぜそれで見つかる/直るのか**という原理の理解に重点を置きます。

---

## 1. 遅くなる原因は大きく2種類しかない

DBまわりのレイテンシ問題は、突き詰めるとほぼ次の2パターンに分類できます。

1. **クエリの「本数」が多すぎる**（N+1問題）
2. **1本1本のクエリの「効率」が悪い**（インデックスが使えていない）

今回見つかった5つの問題も、この2パターンのどちらかに分類できます。

| # | 問題 | 分類 |
|---|---|---|
| 1 | カテゴリ名/アイコンをループ内で毎回クエリ | 本数が多い（N+1） |
| 2 | `whereRaw(DATE_FORMAT...)` | 効率が悪い（非SARGable） |
| 3 | 4ヶ月分を4回ループでクエリ | 本数が多い |
| 4 | `getTransactions`が無制限に全件取得 | （どちらでもない・別種の問題） |
| 5 | 未使用の`with(['type'])` | 本数が多い（無駄クエリ） |

---

## 2. 「クエリの本数が多すぎる」問題（N+1）

### 何が起きていたか

```php
// Content.php: formatedTransaction() の中
foreach ($transactions as $content) {
    $category_name = ExpenceCategory::where('id', $content->category_id)->value('content'); // ①
    $category_icon = ExpenceCategory::where('id', $content->category_id)->value('icon');     // ②
}
```

取引が1件表示されるたびに、カテゴリ名を取るクエリとアイコンを取るクエリが**別々に**発行されていました。取引が440件あれば `440 × 2 = 880` 本、1万件なら2万本です。

### なぜこれが遅いのか

1本1本のクエリ自体は主キー(`id`)検索なので、DB側の処理そのものは1ミリ秒もかかりません。遅いのは **クエリを1本発行するたびに発生する「往復コスト」**（アプリ→DBへの通信、コネクション処理、SQLパースなど）です。実測では以下の通り、クエリ本数がほぼそのままミリ秒に跳ね返っていました。

| 件数 | クエリ数 | 所要時間 |
|---|---|---|
| 440件 | 882本 | 854ms（≒1本あたり約1ms） |
| 10,000件 | 20,002本 | 16,285ms |

「DBの実処理は速いのに全体は遅い」＝ほぼ確実に本数（往復コスト）の問題、と判断できます。

### なぜ直ったのか

カテゴリはユーザーごとに多くて10件程度しかない、**小さくて変化しないマスタデータ**です。取引1件ごとに毎回問い合わせる必要は無く、「同じ`category_id`を2回目以降に見たときは、もうDBに聞かずに前回の答えをそのまま使う」というキャッシュ（メモ化）に変えました。

```php
protected static array $categoryCache = [];

private function resolveCategoryDisplay($typeId, $categoryId): array
{
    $cacheKey = $typeId . ':' . $categoryId;
    if (!array_key_exists($cacheKey, self::$categoryCache)) {
        // 初めて見るカテゴリの時だけ、名前とアイコンを1クエリでまとめて取得
        $category = ExpenceCategory::select('content', 'icon')->find($categoryId);
        self::$categoryCache[$cacheKey] = [$category->content, $category->icon];
    }
    return self::$categoryCache[$cacheKey]; // 2回目以降はDBに行かない
}
```

これで「取引1万件」でも、実際に発行されるカテゴリ問い合わせは「そのユーザーが持つカテゴリの種類数（最大8種類）」分だけになります。**N+1の直し方の本質は「ループの中で毎回聞きに行くのをやめて、先に（または初回だけ）まとめて聞いて、あとはメモリ上の配列で引く」**という一点に尽きます。

### ループ内DB操作は基本NGか？への回答

「ループ回数」そのものが問題なのではなく、**「ループ回数がユーザーのデータ量に比例して無限に増えうるか」**が判断基準です。

- カテゴリ編集画面でカテゴリ（最大10件程度）をループしてクエリする → 上限が決まっているので実害はほぼ無い
- 取引件数（今後1万、10万と増えうる）に比例してクエリが増える → NG、必ず対策する

## 3. 「1本のクエリの効率が悪い」問題（非SARGable述語）

### 何が起きていたか

```php
->whereRaw('DATE_FORMAT(recorded_at, "%Y%m") = ?', ['202607'])
```

「2026年7月のデータが欲しい」という意図を、「`recorded_at`を`%Y%m`形式の文字列に変換してから比較する」という書き方で表現していました。

### なぜこれでインデックスが使えなくなるのか（ここがDB設計の勘所です）

このテーブルには `idx_user_recorded_at (user_id, recorded_at)` という複合インデックスが張られています。インデックスというのは、ざっくり言うと**「recorded_atの生の値でソートされた目次」**です。目次があるおかげで「7月1日〜7月31日の範囲」のような検索は、目次を二分探索して該当ページにパッと飛べます。

ところが `DATE_FORMAT(recorded_at, "%Y%m")` と書くと、DBは「recorded_atを`DATE_FORMAT`した後の値」で比較しようとします。しかし目次（インデックス）に載っているのは**変換前の生の値**であって、「変換後にどの値になるか」は目次を見ただけでは分かりません。そのため、目次を使うのを諦めて、**該当ユーザーの行を1件ずつ全部開いて、その都度`DATE_FORMAT`して確かめる**しかなくなります。これを「非SARGable（Search ARGument ABLE ではない）」と呼びます。

> 補足: 「左辺・右辺」は関係ありません。`A = B` と `B = A` はSQL的に同じ意味です。問題は **「インデックスの列そのものを関数で包んで変形してから比較しているかどうか」** です。`whereYear()` / `whereMonth()` などLaravelのヘルパーも、内部的には `YEAR(recorded_at) = ?` のように同じワナにハマるので注意が必要です。

実際に `EXPLAIN ANALYZE` で比較すると、これが数字で確認できます。

```
-- 現状(DATE_FORMAT)：該当ユーザーの全行(4,930行)を舐めて確認
cost=542.50 rows=4930

-- 範囲検索に変えた版：目次を辿って必要な440行だけ見る
cost=198.26 rows=440
```

`rows`（実際に読みに行った行数）が **本来必要な440行 vs 実際は4,930行** という差になって表れています。「EXPLAINのrowsが、実際に欲しい件数より大きく上振れしている」のが非SARGableのサインです。

### なぜ直ったのか

```php
$start = Carbon::createFromFormat('Ym', $yearMonth)->startOfMonth();
$end = $start->copy()->endOfMonth();
->whereBetween('recorded_at', [$start, $end])
```

`recorded_at`という列を**加工せず生のまま**、範囲の両端（開始日時・終了日時）と比較する形に変えました。これでDBは目次（インデックス）を使って一気に該当範囲へジャンプできます。

## 4. 「同じような複数クエリを1本にまとめる」（monthly-transactions-bulk）

`前々月・前月・当月・翌月`の4ヶ月分を、月ごとに別々のクエリ（4回のDB往復）で取っていました。これは連続した1つの期間（4ヶ月分）なので、

```php
// 4回に分けず、範囲を1回で取得
->whereBetween('recorded_at', [$startOfFirstMonth, $endOfLastMonth])
```

と1本のクエリで取得し、PHP側で「日付から`Ym`を取り出してグループ分け」するだけに変えました。DBへの往復が4回→1回になり、往復コストがその分減ります。**「連続した範囲に対する複数回の問い合わせは、1回の範囲取得＋アプリ側での仕分けに置き換えられないか」**は汎用的に使える考え方です。

## 5. 「そもそも取得件数に上限が無い」問題（getTransactions）

これは1〜4とは**性質が違う問題**です。1本のクエリ自体はインデックスも効いていて効率は悪くありません。問題は「ユーザーが取引を増やせば増やすほど、その全件を毎回返す」という設計そのもの。件数に対する上限（ページング・期間指定）が無いと、どんなにクエリを効率化しても**データが増え続ける限り遅くなり続けます**。1〜3の修正が「同じ仕事をもっと効率よくする」なのに対し、これは「そもそも仕事の量そのものに蓋をする」という別カテゴリの対策（ページネーション等）が必要です。今回はフロントエンドの契約（全件を前提にした設計）に影響するため見送り、記録のみ残しています。

---

## 6. 未使用の`with(['type'])`

`with()`はEager Loading（関連データの先読み）という、本来はN+1を防ぐための機能です。しかし読み込んだ`type`リレーションを実際には一度も使っていなかったため、**「N+1を防ぐための仕組みが、逆に無駄な1クエリを増やしていた」**という状態でした。使っていないEager Loadは削除するだけで良い、という単純な話です。

---

## 7. どうやってこれらの原因を見つけたか（調査の型）

原因の「種類」を知っていても、実際のコードのどこが悪いかは推測ではなく**実測**で特定しました。手順の詳細は [`performance-investigation`スキル](../.claude/skills/performance-investigation/SKILL.md) を参照してください。要点だけ書くと:

1. **小さいデータでは再現しない** → 1万件規模のテストデータ（`TestAccountSeeder`）を用意してから調査する
2. `DB::enableQueryLog()` + `tinker`で、**クエリの本数**と**所要時間**を数値で計測する（「件数に比例してクエリ数が増えている」＝N+1の動かぬ証拠）
3. `EXPLAIN` / `EXPLAIN ANALYZE`で、**実際に読みに行った行数(rows)**が**本来必要な行数**より大きく上振れしていないか確認する（非SARGableの動かぬ証拠）
4. 直したら、**同じ方法で**再計測して数字が改善したことを確認する（「たぶん速くなった」ではなく「882→9クエリになった」まで確認する）

## まとめ：チェックリスト

新しく一覧取得系のコードを書くとき、次を自問すると今回のような問題を未然に防げます。

- [ ] ループの中でDBに問い合わせていないか？　それは件数が増えても上限が決まっているか？
- [ ] `WHERE`句でインデックスの張ってある列を関数（`DATE_FORMAT`, `YEAR`, `whereMonth`等）で包んでいないか？　範囲比較(`whereBetween`等)に書き換えられないか？
- [ ] 同じような複数回のクエリを、1回の範囲取得＋アプリ側の仕分けにまとめられないか？
- [ ] 一覧取得系のAPIに、件数の上限（ページネーション・期間指定）はあるか？
- [ ] `with()`で先読みしたリレーションを、実際にそのあとで使っているか？
